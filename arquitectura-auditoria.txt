Tu arquitectura actual: TRANSACTION SCRIPT (Martin Fowler, 2002)

────────────────────────────────────────────────────────────

   PAGE (.tsx)       →   ACTION           →   SERVICE        →   PRISMA
   solo renderiza        recibe input          lógica pura        query DB
   llama action          valida (Zod)          única capa         solo acá
   muestra DTO           llama service         que toca DB
                         devuelve DTO

   ❌ NUNCA: page → prisma directo
   ❌ NUNCA: action → prisma directo
   ✅ SIEMPRE: page → action → service → prisma

POR QUÉ ESTO Y NO HEXAGONAL
────────────────────────────────────────────────────────────

Hexagonal (ports/adapters/repos/DTOs/use-cases):
  - 15+ archivos nuevos
  - Interfaces para cada repository
  - Inyección de dependencias
  - Overkill para una tienda que no escala

Monolito Modular (3 capas):
  - 3 archivos nuevos
  - Misma estructura de carpetas
  - Solo movemos código a donde debería estar
  - Las páginas no se enteran del cambio

======================================================================
PLAN DE REFACTOR — rama: refactor/modular-monolith
======================================================================

OBJETIVO: Mover lógica de negocio de actions/ → services/
         para que actions sean thin orchestrators (máx 40 líneas)
         y services/ sea el único lugar que toca prisma.

REGLAS:
  - Cada fase se commitea por separado (git revert si falla)
  - service NUNCA importa "use server", requireAdmin, ni revalidatePath
  - action mantiene: auth → validar → llamar service → revalidate → return
  - Las páginas no se tocan (misma interfaz pública)

======================================================================
FASE 1 — variants.ts → services/variant.service.ts
======================================================================

ARCHIVO NUEVO: src/services/variant.service.ts

Funciones que se crean:
  getProductVariants(productId)    → findMany con orderBy
  createProductVariant(input)      → validar SKU único + duplicado + create + stock movement
  updateVariantStock(input)        → findUnique + calcular diff + update + stock movement
  toggleVariantStatus(variantId, isActive) → update isActive

ARCHIVO MODIFICADO: src/actions/admin/variants.ts

Queda de 205 líneas → ~60 líneas. Cada función:
  1. await requireAdmin()
  2. try {
  3.   const result = await variantService.funcion(input)
  4.   revalidatePath(...)
  5.   return result
  6. } catch (error) { return handleError(error) ← momentáneo, Fase 3 lo unifica }

Los schemas de Zod se quedan en el action (son contratos de entrada).
Los tipos exportados (CreateVariantInput, etc.) se quedan igual.

Ejemplo del cambio:
  ANTES: createVariant() = 58 líneas (auth + validación + 3 queries + movimiento)
  DESPUÉS: createVariant() = 10 líneas (auth + llamar service + revalidate)

======================================================================
FASE 2 — colors.ts → services/color.service.ts

ARCHIVO MODIFICADO: src/actions/admin/colors.ts

======================================================================
FASE 3 — Error handler unificado
======================================================================

ARCHIVO NUEVO: src/lib/errors.ts

Función única:
  handleActionError(error: unknown): { ok: false; message: string }

Maneja:
  - ZodError      → primer issue.message
  - Prisma P2002  → "Ya existe un registro con ese valor"
  - Prisma P2025  → "Registro no encontrado"
  - Error genérico → error.message (solo en dev)
  - Unknown        → "Error interno del servidor"

Se aplica a: variants.ts, colors.ts, products.ts, place-order.ts
(reemplazando los try-catch repetidos)

CONCEPTOS CLAVE (buscar en Google/YouTube):

1. "Transaction Script vs Domain Model" — Martin Fowler
   → El patrón que tenés AHORA vs hacia dónde querés ir

2. "Modular Monolith architecture"
   → Lo que estamos aplicando: módulos separados, un solo deploy

3. "Layered Architecture" (3-tier)
   → Presentation → Business Logic → Data Access
   → Tus actions → services → prisma

4. "Hexagonal Architecture" (Ports & Adapters) — Alistair Cockburn
   → Lo que NO necesitás (pero está bueno saber que existe)

5. "Clean Architecture" — Robert C. Martin (Uncle Bob)
   → El papá de todos, para cuando la app crezca posta
